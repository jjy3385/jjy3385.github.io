# MALLOC-LAB

> CSAPP 9장의 내용을 바탕으로 C의 malloc()을 구현해봤습니다.<br>
> 포인터 연산이나 메모리를 직접 다루는 형태의 코딩에 경험이 많지 않았기 때문에 처음엔 매우 애를 먹었지만 해당 과제를 풀어나가면서 뭔가를 해냈다는 성취감을 느낄 수 있었고 그동안 배운 자료구조들이 어떻게 내부적으로 활용될 수 있는지 살짝 감을 잡을 수 있었습니다.<br>

## 📌 묵시적 가용 리스트(implicit free list)

> - CSAPP 책에서 코드를 제공해주는 묵시적 가용 리스트부터 구현함
> - 배치 정책은 first fit, next fit, best fit 모두 구현
> - realloc()은 최적화 덜 됨(이때까지는 realloc() 개선보다는 다른 형태의 리스트 만드는게 급했음)

### 구현조건
- 워드사이즈 = 4바이트
- 모든 블록의 크기는 8의 배수
- 헤더/푸터에 같은 값(사이즈+배치여부) 저장
- 프롤로그/에필로그 블록 사용
- 최소블록 크기는 16바이트

### 생김새(상태모델)
- 문제에 설정된 최소블록 크기 = 16바이트(헤더(4) + 푸터(4))
- 힙에 블록이 배열처럼 들어가 있는 형태<br>
즉, 이전 블록 푸터랑 현재 블록 헤더가 딱 붙어있음<br>
그래서 매크로 함수를 보면 워드만큼 연산해서 헤더/푸터를 찾는 연산을 함
- 각 블록의 헤더/푸터에 있는 사이즈 값으로 이전/다음 블록이 어디 있는지 찾는 구조

    **[그림1]** 묵시적 가용 리스트 블록 모양<br>
    ![2025-08-31-23-56-24.png](/images/2025-08-31-jungle-week07-malloc-lab/2025-08-31-23-56-24.png)
    

- 그림에서 위에서 아래로 내려가면서 주소가 증가
- 헤더,푸터에 사이즈 + 가용비트 저장
- 블록포인터는 페이로드의 가장 작은 주소


### 함수(연산)
1. **find_fit() - 가용 블록 탐색**
    - 배치 정책(`first fit`, `next fit`, `best fit`) 
    - first fit
        - 요청 사이즈 <= 가용 블록 사이즈면 `return` 
    - next fit
        - 이전에 탐색한 블록을 가르키는 `rover` 포인터 추가
        - `rover` ~ 끝(에필로그)까지 탐색 `+` 맨 처음 블록 ~ `rover` 까지 탐색
        -  요청 사이즈 <= 가용 블록 사이즈면 `return` (= first fit 이랑 똑같음)
    - best fit
        - 요청 사이즈 == 가용 블록 사이즈면 바로 `return`
        - 그렇지 않으면 전체 리스트를 모두 탐색
     
2. **place() - 블록 할당**
    - 요청 사이즈와 가용 블록의 사이즈 비교
    - 둘의 차이가 최소 블록 크기보다 크면
        - 요청 사이즈만큼 할당, 남은 부분은 분할
    - 최소 블록 크기보다 작으면
        - 블록 전체 할당(내부단편화 감수)

## 📌 명시적 가용 리스트(implicit free list)

> - 묵시적 가용 리스트는 블록 탐색 시 모든 블록을 전부 탐색함
> - 즉,할당된 블록은 사실 탐색할 필요가 없는데도 탐색하기 때문에 속도(처리량)가 느림
> - 명시적 가용 리스트는 이런 문제를 해결할 수 있는 구조

### 구현조건
- 사이즈는 8의 배수
- 최소 블록 크기는 24바이트<br>
헤더(4) + 푸터(4) + PRED(8) + SUCC(8) 
- 연결 리스트에는 가용 블록만 연결

    > - 묵시적 가용 리스트의 헤더/푸터 형태 + 에필로그/프롤로그 블록도 그대로 사용함<br>
    > - 구현 조건은 아니지만 막상 묵시적에서 명시적으로 넘어갈 때, 이 구조도 그대로 가져가는건지 고민이 되는 부분이었음.<br>
    > - 헤더/푸터 형태는 그대로 쓰는 이유가 명확함, 블록 간 연결에 꼭 필요함<br>
    > - 프롤로그/에필로그 블록은 필수는 아님<br>
    다만 그건 묵시적 가용 리스트에서도 마찬가지였음<br>
    즉, 얘네는 코드를 단순하게 해주고 조건처리를 편하게 해줘서 쓰는 블록이라 그대로 쓰는게 좋음
    

### 생김새(상태모델)
- 가용 블록만을 연결한 이중 연결리스트 구조
- 각 가용 블록은 이전 블록과 다음 블록을 가르키는 포인터가 있음<br>
단, 할당된 블록은 해당 포인터들이 필요없음<br>
따라서 할당 시 해당 포인터들은 사용자 데이터에 의해 덮어써짐<br>
(그래서 블록포인터가 묵시적 가용 리스트와 똑같이 바로 헤더 아래를 가르킴)
    **[그림2]** 명시적 가용 리스트 블록 모양<br>
    ![2025-08-31-23-55-54.png](/images/2025-08-31-jungle-week07-malloc-lab/2025-08-31-23-55-54.png)

### 함수(연산)
1. **insert_free_list() - 가용 리스트에 블록 추가**
    - 배치 정책은 `first fit` 으로 구현(LIFO)
    - 새로 추가되는 가용 블록이 루트 블록
2. **delete_free_list() - 가용 리스트에 블록 제거**
    - 이전블록 포인터와 다음블록 포인터와 제거되는 블록의 연결 끊기
    - 이전블록 포인터와 다음블록 포인터 잇기
3. **coalesce() - 가용 블록 연결**
    - 이전 블록/다음 블록이 할당/가용인 경우에 따라 병합을 진행하는 건 묵시적 가용 리스트와 같음<br>
    즉, 연결리스트로 이전/다음 블록을 보는게 아니라 기존처럼 헤더/푸터로 이전/다음 블록을 찾음<br>
    왜냐하면 실제 블록이 메모리에서 붙어있어야 이전/다음 블록이여야 병합할 수 있기 때문
    - 위의 두개 함수를 이용해서 이전/다음 블록의 연결을 끊어주고 다시 가용 리스트 블록에 추가해줌
4. **realloc() - 할당된 메모리 블록의 크기 변경**
    - 묵시적에서 놓친 부분까지 모두 적용하여 개선사항 추가
        - 사이즈 줄일 때
        - 블록 병합(3가지 케이스 모두 고려되도록)

## 📌 분리 가용 리스트(segregated free list) - 맞춤

> - 지금까지는 가용 리스트가 하나였음
> - 분리 가용 리스트부터는 가용 리스트 자체를 여러개로 둠
> - 나누는 기준은 블록 사이즈에 따라 구간(클래스)별로 나눔
> - 이렇게 하면 탐색이 더 빨라질 수 있음


### 구현조건
- 사이즈는 8의 배수
- 명시적 가용 리스트와 거의 비슷
- 사이즈 별로 가용 리스트를 관리하는 배열 존재<br>
따라서 해당 배열의 원소는 사이즈에 맞는 가용 리스트끼리 연결되어야 함 

### 생김새(상태모델)
- 가용 블록의 생김새는 명시적 가용 리스트와 같음
- 명시적 가용 리스트는 연결 리스트가 하나였다면<br>
분리 가용 리스트는 연결 리스트가 사이즈 별로 여러개인 형태
- 클래스를 나누는 기준은 사이즈로 보통 2의 제곱수를 기준으로 함<br>
즉, `2 ~ 3`, `4 ~ 7`, `8 ~ 15`, `16 ~ 31`, `32 ~ 63`, `64 ~ 127`, `128 ~ 255` .... 
- 해당 클래스(사이즈 구간)에 속하는 가용 블록끼리 연결한 이중 연결리스트 형태임 

    **[그림3] 분리 가용 리스트 - 다중 연결 리스트**<br>
    ![2025-09-01-00-41-43.png](/images/2025-08-31-jungle-week07-malloc-lab/2025-09-01-00-41-43.png)

### 함수(연산)
1. **get_list_index() - 가용 리스트 인덱스**
    - 사이즈 별 가용 리스트의 인덱스 반환

    > 분리 가용 리스트(맞춤)의 경우엔, 개념적으로는 어려웠지만 코드 자체는 명시적 가용 리스트에서 많이 바뀌진 않았음<br>
    또한 성능 자체도 큰 차이가 없었는데 이건, 처리량(탐색속도) 점수가 명시적 가용 리스트에서도 이미 만점이였기 때문임, 분리 가용 리스트는 탐색 속도가 획기적으로 좋아지지만 단편화는 명시적 가용 리스트와 그다지 차이가 없음<br>
